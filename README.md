# MaxKB 知识治理工作台

支持文档入库和相似段落扫描。前后端由 FastAPI 提供，PostgreSQL 独立运行。

## 从源码构建运行

需要 Docker Engine、Docker Compose V2 和可下载构建依赖的网络。在源码根目录使用 `compose.yaml`；安装包使用 `docker/compose.yaml`。

首次没有根目录 `.env` 时，编辑 `install/.env.example`，配置 `WORK_DIR`、数据库密码和 `ALLOWED_ORIGINS`（网页实际访问的协议、主机和端口），然后执行：

```bash
bash install/install.sh --init-env
# 自定义 WORK_DIR 时改为脚本输出的配置文件路径。
ln -s /opt/maxkb-remove-duplicates/.env .env
```

初始化会生成加密密钥和管理员初始密码。已有 `.env` 时直接使用现有配置，容器内数据库主机应配置为 `DB_HOST=postgres`，并检查 `IMAGE_VERSION=v1.0.0`；不要保留指向其他数据库的 `DATABASE_URL`。

在源码根目录构建并启动：

```bash
docker compose up -d --build
```

也可以分别执行：

```bash
docker compose build
docker compose up -d
```

应用通过同一个 `docker/Dockerfile` 构建，缺少 `postgres:18` 时自动拉取。数据保存在 `WORK_DIR/maxkb-remove-duplicates/` 的 `postgres/`、`ingestion/`、`documents/`，默认位于 `/opt/maxkb-remove-duplicates/`。后续修改根目录 `.env`；使用上述符号链接时，它与工作目录配置是同一个文件。

查看日志和停止服务也在源码根目录执行：

```bash
docker compose logs -f app postgres
docker compose down
```

切换源码构建和安装包运行时，使用相同的工作目录、数据库配置和加密密钥。

## 下载安装包

在 [GitHub Actions](https://github.com/linyuiu/maxkb-remove-duplicates/actions/workflows/build-images.yml) 点击 **Run workflow**：

- `architecture`：选择 `amd64`、`arm64` 或 `both`。
- `image_tag`：镜像版本，默认 `v1.0.0`。

构建完成后，从 **Artifacts** 直接下载对应架构的 `.tar.gz`，解压一次即可。安装包已包含应用和 PostgreSQL 18 镜像。安装脚本会从 `docker/images/` 加载，目标机器无需拉取这两个镜像。构建摘要提供安装包的 SHA-256 校验值，产物保留 14 天。

## 安装

服务器需要 Docker Engine、Docker Compose V2 和 Bash。

PostgreSQL 18 的数据固定存放在服务目录的 `postgres/18/docker/` 下。升级时使用原来的 `WORK_DIR`，全新安装时使用空的服务目录。

1. 编辑 `install/.env.example`，设置 `WORK_DIR`、数据库密码、访问地址等参数。`WORK_DIR` 默认 `/opt`，服务目录为 `/opt/maxkb-remove-duplicates`。执行安装的用户需要有权创建并写入服务目录，也可以填写其他路径。
2. 在安装包目录执行：

```bash
bash install/install.sh
```

脚本会加载 `docker/images/` 中的镜像，并生成以下服务目录：

```text
WORK_DIR/maxkb-remove-duplicates/
├── .env
├── compose.yaml
├── postgres/18/docker/  # PostgreSQL 18 数据
├── ingestion/      # 入库文件和解析产物
└── documents/      # 待入库的本地文档
```

首次启动自动创建数据库、业务表和管理员。通过部署主机的 `WEB_PORT` 访问，默认端口 8080；管理员初始账号密码在生成的 `.env` 中查看。

`ALLOWED_ORIGINS` 用于 CORS 和写请求的来源校验。填写浏览器实际访问页面的协议、主机和端口，例如 `http://192.168.1.20:8080`。多个地址用英文逗号分隔，不加空格、路径或末尾斜杠。

正式安装或升级会将包内镜像版本同步到服务目录 `.env` 的 `IMAGE_VERSION`，保留其他配置。安装后在服务目录的 `.env` 中修改运行配置。已有数据库及管理员密码也不会随配置修改自动重置。

仅生成配置和目录、不操作 Docker：

```bash
bash install/install.sh --init-env
```

## 启动和停止

进入生成的服务目录后执行，无需再指定配置文件路径：

```bash
cd /opt/maxkb-remove-duplicates

docker compose up -d                    # 启动
docker compose down                     # 停止，保留数据
docker compose ps                       # 状态
docker compose logs -f app postgres     # 日志
docker compose restart                  # 重启
docker compose up -d --force-recreate    # 修改 .env 后重新创建容器
```

备份数据库、`ingestion/`、`documents/` 和 `.env`，保留原来的 `ENCRYPTION_KEY`。

## 使用

- **知识入库**：在“入库设置”配置 MaxKB API、Bearer Key 和 MinerU；支持 PDF、Word、Excel，以及目录和 SSH 来源。公共连接复用的是 MaxKB API 地址和 Key。
- **本地目录**：把文档放进服务目录的 `documents/`，网页选择“映射”后手动扫描并提交。入库成功后，原文件会归档到 `documents/已处理文档/`，需要读写权限。
- **重复片段**：添加 MaxKB 数据库连接，选择知识库、阈值和手动/定时任务。扫描前显示数量与预计耗时，结果展示完整段落，修改及删除通过 MaxKB API 执行。
- **删除数据源**：数据源卡片支持删除。请先删除关联扫描任务，等待活动扫描结束或取消，并核实结果不明确的源操作；删除后保留扫描记录和操作历史，清除平台保存的该数据源连接凭据，不删除 MaxKB 中的内容。
- **停用文档**：添加或编辑去重任务时可关闭「包含停用文档」。预估和实际扫描会一起排除停用文档，已有任务默认继续包含。
- **向量就绪检查**：预估及执行前检查所选知识库的正文段落；缺少向量、等待/正在向量化、失败或未知状态都会阻止扫描，并提示知识库、文档及异常数量。定时任务在扫描历史中记录未执行原因，等待下次触发。
- **删除源段落/文档**：接口回读确认删除成功后，所有对应的相似对自动标为已处理，从待处理筛选中移除；保留原文快照和关联操作记录。
- **修改源段落**：接口回读确认修改成功后，关联旧结果标记为“内容已变化，需重新扫描”，从待处理筛选中移除；保留扫描快照及修改前后文本，重新扫描后再处理。
- **删除扫描记录**：清理本次扫描结果和快照，保留操作文本历史，不删除 MaxKB 源数据。运行中的任务需先取消。
- **修改密码**：点击右上角用户菜单，验证原密码并填写两次新密码（至少 12 个字符），成功后重新登录。

MaxKB API 地址示例：`http://maxkb.example.com:18080/admin/api`，请替换为实际地址。系统数据库与 MaxKB 源数据库需分开配置。

Compose 通过服务目录 `.env` 的 `IMAGE_VERSION` 选择镜像标签。源码修改后执行 `docker compose up -d --build`。原地升级时，在新包的 `install/.env.example` 填写原来的 `WORK_DIR`，备份服务目录后执行 `bash install/install.sh`。安装脚本会验证包内镜像已加载，再更新 `IMAGE_VERSION` 并重启服务。

## 扫描计算与资源配置

相似度扫描在应用服务器中执行分块矩阵乘法。MaxKB 数据库只负责校验和流式读取正文向量，读取完毕即关闭源连接。所有符合范围条件的 chunk 组合都会比较，不截断候选。

快照使用二进制 COPY 逐条接收向量，每 1000 条提交一次本地临时索引；不保留 1000 条正文或向量的读取列表。随后按段落读取正文，每段在本次扫描中只传输、保存一次。正文批次所对应的 chunk 累计到 5000 条，或序列化缓冲达到约 64 MiB 时，通过二进制 COPY 提交，并提交剩余尾批。段落不可拆开写入，因此单批 chunk 数可能略超 5000；计数与正文快照同事务提交。读取和批次写入期间定期续租，批量插入结束后才短暂锁定运行记录校验租约，取消或租约失效会回滚整批。

单段正文、标题及元数据的原始文本合计最多 8 MiB，超过时在源端拒绝传输并报告段落 ID，不截断正文。该限制与 64 MiB 写入缓冲用于控制读取和暂存占用，不是进程总内存上限。向量先落盘，正文写入阶段再更新已提交的 chunk 计数。二进制 COPY 的超时按每次等待源数据计算（120 秒），不把正文写入耗时算作源查询超时。

每次新扫描记录分阶段墙钟耗时，可在扫描记录或结果页打开「耗时分析」，并导出 JSON。统计约每 10 秒保存到独立的计时表，结束、失败或取消时保存最终统计；后端同时输出 `scan_timing` 日志。覆盖源库连接、模型及就绪校验、向量与正文读取、本地归一化及落盘、矩阵块读取、矩阵乘法、阈值过滤与聚合、结果保存、进度更新和最终校验。结果写入进一步拆分缓冲等待、排序、摘要、COPY、服务端合并、事务末尾批次确认与提交。

累计耗时包含子阶段，自身耗时扣除子阶段。计算及源库读取线程与结果写入线程分别统计；两个线程可以重叠，不能将线程耗时或父子累计耗时相加作为执行总耗时。次数是计时区间调用次数，不等同于 SQL 条数；SQL 区间包含网络等待与客户端处理，提交区间包含数据库提交响应；扫描专用写连接持续复用，结束时才归还。计时不含排队及最终统计自身的保存请求；后台续租线程不计入扫描线程阶段耗时。阶段计时只累计次数、总耗时和最大值；另外记录每个 COPY 批次，不记录逐条向量或段落内容。旧扫描及已经启动的扫描不会补算历史计时。

「耗时分析 → 批次与索引」可查看每批 COPY、merge 耗时、行数、重试次数和确认状态，并切换每批或每万行耗时曲线。导出的 JSON 包含 `batch_series`：时间相对于本次扫描开始，COPY/merge/commit 为该逻辑批次各次尝试的累计墙钟时间；`attempts` 与 `recovered` 标记重试/重连确认，未确认的批次不会计作成功。为控制内存和导出体积，最多保存前 2048 加最近 2048 条批次记录，省略数写入 `batch_series_omitted`；后端 `scan_batch_timing` 日志保留每个批次的完整记录，均不包含正文和连接凭据。

`index_io` 保存比较写入开始前、写队列清空后的 `pg_statio_user_indexes` 快照及差值，排除最终 `COUNT` 校验。采集时请求本写连接刷新待发布统计，不重置全库统计。按索引记录读块、命中块、大小与 OID；检测到重启、已知统计重置或索引重建时标记统计无效。计数包含同库其他连接活动，读块也可能命中操作系统缓存，不能全部视为物理磁盘读取。诊断采集失败会记录原因，不改变扫描结果。

任务中的「矩阵块大小」默认 1024，最大 4096。运行时按 `.env` 中的工作区预算自动缩小块，每次只加载两块向量、一块分数矩阵，矩阵输出先在内存中跨块合并，匹配结果最多每 50,000 个唯一段落对提交一次；剩余尾批或达到内存预算时提前提交。进度百分比按已完成的有效比较次数计算，每 5 秒最多发布一次，结束时强制发布。

结果写入由一个专用线程完成，复用一条写连接；该连接使用 `work_mem=64MB`，归还前执行 RESET 并恢复借出前的值，不改变其他池连接的排序内存。队列最多暂存一批，计算端在缓冲满时等待。结果缓冲按对象大小保守计量，预算为 128 MiB，涵盖计算端待写、排队及写入中的批次，独立于矩阵计算工作区预算；均不是进程总内存硬限制。写入临时表在连接建立时创建，事务提交后自动清空，不逐批建表。

结果批次执行 `COPY → UPSERT → 条件更新运行记录 → COMMIT`。运行记录只在事务末尾短暂锁定，结果及新增/更优/未变化计数、批序号和摘要同事务提交。断线后先确认批序号与摘要，再决定是否重试，避免提交响应丢失时重复累加。已有段落对只接受更高分或同分且向量 ID 更小的结果，保留结果 ID 和处理状态。完成运行前等待所有写入确认，并核对比较数量和最终结果总数。取消检查与 15 秒续租独立运行。

| 配置                | 默认值   | 作用                                                                                   |
| ------------------- | -------- | -------------------------------------------------------------------------------------- |
| `SCAN_MEMORY_MB`    | `2048`   | 矩阵工作区预算，单位 MiB，范围 32～2048；不是整个应用或容器的内存上限                  |
| `PG_SHARED_BUFFERS` | `2GB`    | Compose 中 PostgreSQL 的共享缓存，需重建数据库容器生效；源码后端不会修改远程数据库参数 |
| `SCAN_THREADS`      | `4`      | 数学库最大线程数，受可用 CPU 核数限制                                                  |
| `SCAN_TEMP_DIR`     | 自动选择 | 临时向量快照目录，应使用有足够空间的磁盘目录                                           |

部署前确认 PostgreSQL 容器的内存上限和宿主机可用内存：`shared_buffers` 之外还需要为连接、排序、操作系统及应用留出空间，不能把容器总内存限制仅设为 2 GiB。可通过 `.env` 的 `PG_SHARED_BUFFERS` 覆盖模板默认值；已有 `.env` 不新增该字段时，Compose 同样使用 2GB 默认值。

Docker 默认把临时文件放在 `/data/ingestion/.scan-tmp/`。源码运行时，若配置了 `INGESTION_DATA_DIR` 则使用该目录下的 `.scan-tmp/`，否则使用系统临时目录。正常完成、失败或取消后清理本次文件。每个向量按归一化 float64 保存，120,832 个 768 维向量约需 708 MiB 临时向量空间，另需元数据索引空间；这些文件不会整体加载到应用内存。不要将临时目录放在 tmpfs 等内存文件系统上。

向量计算使用 float64，数学库与 pgvector 的浮点累计顺序不同，阈值边界可能出现微小分数差异。预估按「快照 + max(矩阵计算、结果写入) + 最终校验」的流水线关键路径计算，计算侧扣除等待写队列的时间，避免把并行阶段相加或重复计算快照。矩阵工作量按实际块形状计算；阈值和同段落/同文档排除仍决定有效比较数与结果写入量，排除条件并不会省去已经执行的矩阵乘法。

预估只参考成功且计时完整、同数据源/知识库范围、同向量模型和阈值的 COPY 流水线扫描。优先使用实际矩阵块大小、线程数、工作区预算、5 万条写入批次、排序内存、数据库缓存和运行环境一致、数据规模接近的样本；索引规模大幅变化或跨过共享缓存容量时也降低为参考样本。配置不同或缺少完整执行标记时显示「参考历史」并放宽范围。旧 SQL/ORM 扫描不参与新预估；无可用样本时也会按默认性能规则给出初始耗时范围，允许正常发起首轮扫描；完成后再使用实测阶段计时校准。`SCAN_ESTIMATE_COMPARISONS_PER_SECOND` 不再用于新模型。数据统计不执行向量比较，结果密度取自相同范围历史，因此内容或重复率显著变化后仍须重新校准。

没有历史时，初始规则使用同一关键路径公式：向量与正文快照按读取吞吐估算；计算按实际矩阵块数量、维度及线程数修正；候选结果按默认匹配率估算，再计入每 5 万条批次的写入和事务开销。首批积攒及尾批写入单独计入流水线，避免小任务误算为完全并行。默认范围为初始估算值的 0.5～3 倍，属于经验估计，不是实测性能或保证区间。

| 初始预估配置                            | 默认值     | 含义                                                  |
| --------------------------------------- | ---------- | ----------------------------------------------------- |
| `SCAN_ESTIMATE_VECTOR_ROWS_PER_SECOND`  | `2000`     | 768 维向量快照处理条数/秒                             |
| `SCAN_ESTIMATE_PARAGRAPHS_PER_SECOND`   | `3000`     | 正文快照处理段落数/秒                                 |
| `SCAN_ESTIMATE_MATRIX_CELLS_PER_SECOND` | `40000000` | 768 维、1024 大小矩阵块、4 个数学库线程的综合计算基准 |
| `SCAN_ESTIMATE_RESULT_ROWS_PER_SECOND`  | `15000`    | 结果 COPY 与合并处理条数/秒                           |
| `SCAN_ESTIMATE_MATCH_RATIO`             | `0.001`    | 初始假设 0.1% 的有效 chunk 对产生候选，范围 0～1      |

实际匹配密度、源库链路和数据库负载会影响时间。初始假设保存在预估结果的 `initial_assumptions` 中，便于检查和调整；有可用历史时优先采用历史，以上参数不覆盖已校准结果。
